# 科研 AI 协作工作流 v1.1

> 适用于「研究者 + ChatGPT（科学讨论与审查）+ OpenCode（本地执行）+ Git（版本和证据）」的轻量协作。无需开发平台或依赖特定模型。
>
> 状态：**v1.1 可投入试用**；单项目 R0—R2 有实际试运行记录；**跨项目可迁移性尚未实测**。本仓库不是自动化治理程序，规则不等于自动执行保证。

## 1. 它解决什么，不解决什么

要解决：研究问题被对话或执行 AI 悄悄改写；新算法/阈值/基线未经批准进入实验；多轮后无法分辨事实与推断；研究者看不懂结果；AI 不知何时停止。

不解决：自动证明数学结论、保证论文创新性、代替研究者作决定、自动验证 AI 是否执行过本地命令。重要结论仍需要证据与独立复核。

**最终控制权**：研究方向、科学主张、假设、实验口径、算法机制、重要阈值和基线由研究者批准；AI 可提出理由和备选方案，但不能把建议当指令执行。

## 2. 成品组成：一份说明书 + 五个模板 + 一个案例

```text
research-ai-workflow-v1.0/
├── README.md                     # 本说明书：研究工作流与使用方法
├── templates/
│   ├── RESEARCH_ACTIVE.md        # 默认分支：指向当前活动研究
│   ├── AGENTS.md                 # 活动分支：OpenCode 权限边界
│   ├── PROJECT_STATE.md          # 活动分支：当前科学问题/决策/证据
│   ├── RESEARCH_POOL.md          # 活动分支：本项目文献索引与研究想法
│   └── ROUND.md                  # 每一轮复制一份，填目标/授权/交接
└── examples/
    └── MOSAIC_R1_R2.md          # 已完成的真实流程案例及证据限制
```

这是**文件模板包**，不是现成的项目仓库；不要把其中的占位符内容当成已批准的研究协议。

## 3. 研究生命周期：从想法到下一轮（固定五个阶段）

| 阶段 | 研究者与 ChatGPT | OpenCode | 允许推进的门槛 |
|---|---|---|---|
| ① 问题形成 | 阅读文献、明确研究问题/新意/反例/强基线；标注证据等级 | 只读盘点（经授权） | 研究者确认问题及不研究什么 |
| ② 计划冻结 | 确定假设、可证伪条件、预算、对照、指标、文件与审批边界 | 可估算技术实现成本，不改科学定义 | 研究者明确批准一份 `ROUND.md` 任务 |
| ③ 受控执行 | 不在中途随意换目标；处理审批申请 | 按批准范围编码/实验/留证据；遇科学变化停在边界 | 指定验收物完成，未越权 |
| ④ 审核理解 | 核对代码和结果；区分事实/报告/推断/未知；确认自己理解关键方法 | 提供可追溯、可复现的交接 | 研究者明确验收或退回 |
| ⑤ 决策归档 | 接受/修改/放弃，并说明原因；更新状态、知识池、下一轮候选 | 不自动开始新一轮 | 新一轮必须重新授权 |

**重要**：阅读论文形成的新想法先登记本项目的 `RESEARCH_POOL.md`；全局阅读笔记可保存在独立的 `research-library`。除非研究者同意，不得自动覆盖当前目标。

## 4. 如何在新项目上使用（无需新软件）

**步骤 A — 建立研究入口**

1. 新建一个研究 Git 仓库；把 `templates/AGENTS.md`、`PROJECT_STATE.md`、`RESEARCH_POOL.md` 放到**活动研究分支根目录**。
2. 把 `templates/RESEARCH_ACTIVE.md` 放到仓库**默认分支根目录**，填写实际仓库和活动分支。如果只用一个分支，两者可以相同。
3. 将 `templates/ROUND.md` 复制为活动分支中的 `research/rounds/R001.md`。首次处于 `DRAFT`，**不能因为文件存在就认定研究者批准**。
4. 填写状态文件：研究问题、主张、可证伪条件、强基线、范围、证据和未知。没有结论写 `UNKNOWN`，不要填假设性的数字。
5. 让 ChatGPT / OpenCode 按 `RESEARCH_ACTIVE.md → PROJECT_STATE.md → AGENTS.md → 最新已授权轮次` 读入。涉及文献才额外读 `RESEARCH_POOL.md`，无需每次把所有旧报告读一遍。

**步骤 B — 在 ChatGPT 做科学论证**

使用下面的启动语句（先确保 ChatGPT 确实能读取相应文件；不能访问时提供相关文本）：

> 请按本项目的 RESEARCH_ACTIVE.md / PROJECT_STATE.md / AGENTS.md 与 research-ai-workflow v1.0 规则讨论。我当前想验证【研究问题】。先核查已有强基线、明确可证伪假设及主要风险；区分已知事实与推断。暂不安排编码、改协议或启动实验，每轮最多提出两个关键问题。

**步骤 C — 冻结单轮任务**

在 `research/rounds/R00X.md` 填写：问题、非目标、允许/禁止操作、预算、输出、验收标准、停止条件、批准记录。在研究者发出**明确授权**后，OpenCode 才可执行。普通工程修复也须服从当轮授权范围；能自主修复不等于可以自主加任务。

**步骤 D — 发送 OpenCode 指令**

> 读取 RESEARCH_ACTIVE.md，核对当前 Git 分支/HEAD/工作区，再读 PROJECT_STATE.md、AGENTS.md 和研究者已批准的 `research/rounds/R00X.md`。只执行该轮允许事项。若科学方法、指标、约束、基线、实验范围需改变，先给出旧法/新法/必要性/影响/验证方式，停止受影响操作等待批准。完成后填写证据交接与实际变更清单，勿自动开启下一轮、提交或推送（除非本轮明确授权）。

**步骤 E — 独立验收**

研究者/ChatGPT核查：Git diff 是否越权、测试运行与跳过情况、原始数据与配置是否可溯源、结论是否有证据、审批是否满足、是否按时停止。**ChatGPT 只能核对其实际可访问的证据；本地未共享的运行日志不能声称独立验证。**通过后由研究者更新 `PROJECT_STATE.md`，再决定新一轮。

## 5. 科学变更审批：五格申请，不允许先做后补

任何影响科学结论或可复现性的变化（研究主张、算法、证书、数据筛选、阈值、指标、基线、场景、终止条件等）先提交：

| 内容 | 必须回答 |
|---|---|
| 旧方法 | 当前冻结版本是什么？证据路径/提交是什么？ |
| 新方法 | 要改变哪个机制/参数/协议？ |
| 必要性 | 为什么原方法不能继续？反例或失败证据？ |
| 预期影响 | 对结论、实验可比性、UNKNOWN、成本和复现的影响？ |
| 验证方式 | 最小验证、回归/消融、需要重跑的数据范围？ |

**审批状态**：`PROPOSED → APPROVED / REJECTED / DEFERRED`。缺少可查找的明确研究者决定，就保留 `PROPOSED` 或 `UNKNOWN`；仓库历史代码、AI 建议、测试通过都不算批准。

## 6. 最小研究交接（不要堆报告）

每轮交付以 **200 字以内摘要 + 一张证据表 + 一张变更/测试表** 为默认；技术细节用链接指向代码、提交、日志、原始实验文件，不在轮次文档里全文复制。主张标记：

- **已核实事实**：源码/commit/可读取数据或已实际验证的测试；说明核实者与范围。
- **报告声称**：执行者提供的结果，暂未独立复核。
- **推断/假设**：根据证据作的解释，附条件和反例。
- **UNKNOWN**：缺证据、未完成、审批未决；不能升级为 PASS/已证实。

实验任务应记录：代码 SHA、配置 SHA 或文件、数据版本、随机种子、运行命令、环境、样本与统计口径、生成位置，以及 dirty/clean 状态。测试必须记录 **passed/failed/skipped**，不能把 skip 算通过。

## 7. 何时需要程序？

v1.0 **不需要专用程序**。先用 Git diff、Markdown 和现有测试工具；当重复遇到相同的人工审计成本时，再按单独授权开发小脚本（例如检查越权修改、收集试验元数据）。不要先建设科研管理平台。

## 8. 当前验证状态和使用边界

- 已观察：`mosaic-planning` R0—R0.2 恢复状态/权限，R1 完成只读审计并提出真实科学审批申请，R2 在有限授权下增加证据 JSONL 导出及测试。
- GitHub 已核对相关提交和允许文件范围；部分本地归档与执行日志不可由远程仓库独立复验。
- **尚未验证**：换一个科研项目时是否零改造适用；长周期研究、多用户团队协同、真正无人监管情况下的权限遵守。
- 当前 v1.0 可以直接用于新项目的**受控试运行**，不能宣称对所有科研活动的有效性已获证明。

详细案例：[`examples/MOSAIC_R1_R2.md`](examples/MOSAIC_R1_R2.md)。

## 9. Zotero 与独立论文库（v1.1 增补）

- **Zotero** 是文献题录、PDF、标注和原始笔记的主库，不修改其数据库文件。
- **research-library** 是跨项目的可检索知识库：一个论文 ID 对应一份结构化 Markdown；`topics/` 可以交叉索引同一论文，不复制笔记；来源可以是 Zotero 导出的题录和笔记。
- **各研究项目的 `RESEARCH_POOL.md`** 只记录本项目采纳的论文引用、与假设的关系和待决想法。研究决策、批准记录仍留在 `PROJECT_STATE.md` 和轮次文件。
- Zotero 的 **题录导出不等于论文全文分析**；原始笔记不等于独立验证；无法看到原文的方法与结果时明确写 `NOT_READ` / `UNVERIFIED`。
- 先按需导出小范围 Zotero collection，核查 3–5 篇转换效果，再扩大范围。保持 Markdown 输出可重复，不在导入时批量覆盖人工整理的结论。
- 不把受版权限制的论文 PDF 或大段原文直接提交到 GitHub；优先保存 DOI/链接、页码、极短的证据摘记与自己的分析。

本模板包不包含论文导入程序，也不要求使用 Zotero 插件。配套的可选 `research-library-starter-v1.0.zip` 含目录、笔记模板与 OpenCode 提示词。未进行第二研究项目的迁移验证。

### 从 v1.0 升级

无需更改已运行的科研项目或重新启动 R0—R2。只需在新项目中使用本版 `RESEARCH_POOL.md`（或将原表保留，增加全局库引用链接），并在需要时使用独立 `research-library`。现有审批规则及轮次模板不变。
